## 0. 第一性原理

### 0.1 我们到底在解决什么问题

**SEO 时代结束**。Google AI Overview 把 #1 自然位 CTR 从 28.5% 砍到 11.2%(Ahrefs 2024)。中国大陆同步发生:豆包 MAU 2.26 亿、DAU 破亿,用户越来越多直接问 AI 而不是去搜索引擎本身。

**新流量入口在 AI 答案里**。这意味着:
- 一个口腔医院能不能被新患者发现,不再取决于"百度排名第几",而是"豆包 / 元宝 / DeepSeek 在回答相关问题时**有没有提到你的医院 / 医生 / 项目**"。
- 传统 SEO 工具(关键词 / 反链 / SERP)对 GEO 完全没用。
- 完全不同的优化逻辑、完全不同的工具。

### 0.2 GEO Studio 的唯一 KPI

**SOV(Share of Voice)× 真实归因转化**。

不是发布数量,不是变体数量,不是 worker 跑了几次。是这两条:

- **SOV**:在所有相关问题的 AI 答案里,本品牌被提到的次数 / (本品牌 + 主要竞品)被提到的次数
- **归因转化**:有多少新患者来店,能溯源到具体哪条发布内容

任何一个功能,如果回答不了"它如何提升这两个数字",就是噪声。

### 0.3 我们的三条护城河(顺位重要)

按从浅到深:

1. **完整闭环**(护城河 1):市面工具只做监测(Profound、Athena)或代发(GhostKnife),没有完整闭环。我们做"知识 → 写 → 审 → 发 → 追踪 → 归因 → 反推" 7 层。
2. **知识库根基**(护城河 2):AI 引擎给"凭空 AI 写的内容"降权。只有用真实临床数据 / 论文引用 / 医生背书的内容,引用率才高。我们的知识库接入是别人复制不了的资产。
3. **转化归因闭环**(护城河 3):靠暗号 + 多钩子,把"AI 答案 → 患者来店"做成可溯源链路。竞品如果做这个,需要 6-12 个月技术 + 客户端推广,我们已上线。

3 条护城河叠加,构成 12-18 个月的窗口期。

## 1. 产品愿景

### 1.1 一句话定义(对内)

> GEO Studio 是 **以专业知识库为根基** 的 AI 内容工厂,把高客单价品牌的 **专业事实** 系统性地翻译成 **AI 引擎倾向引用 + 真实带来转化** 的内容形态,跨多平台真人矩阵投放,可溯源到 ROI。

7 个关键词被加粗。每个加粗都对应一层架构。

### 1.2 一句话定义(对客户)

> "你写一份专业素材,我们帮你在豆包 / 元宝 / ChatGPT 的答案里被提 100 次,带来 30 个真实到店患者。"

### 1.3 不做的事(明确边界)

| 不做 | 为什么 |
|---|---|
| 完全 AI 凭空生成原创(无知识根基) | AI 引擎对纯 AI 内容降权,SOV 反而下降;事实质量低,合规炸弹 |
| 自动登录 / 自动发布员工号 | 平台反爬一封一片,合规 + 风控 + 声誉三重风险(D3) |
| 付费推广采买 | 百度 / 抖音 feed 流是另一个市场,工具市面已多,差异化弱 |
| 通用 SEO | 关键词 / 反链 / SERP 那套和 GEO 没关系 |
| MCN 内容代生产 | 把"工具"变成"服务",护城河消失,毛利从 70% 砍到 20% |

## 2. 7 层飞轮架构

### 2.1 整体图景

```
                  ┌─────────────────────────────────┐
                  │  [反馈环]                        │
                  │  哪些素材带来最多转化?          │
                  │  → 告诉医生重点写这类           │
                  │  → 知识库 +1                    │
                  │  → 飞轮加速,效率指数级提升     │
                  └────────────┬────────────────────┘
                               ↑
[1] 知识根基 ──→ [2] 角度爆破 ──→ [3] 平台变体 ──→ [4] 三道门 ──→ [5] 派单 + 真人发 ──→ [6] AI 追踪 ──→ [7] 转化归因
   (md / 病例)    (RAG + LLM)     (GEO 9 法)        (合规)         (40 员工矩阵)        (豆包/元宝)     (暗号 + 漏斗)
        ▲
        └─── 知识库扩充
```

每一层一节,讲设计原则 + 现状 + 目标。

### 2.2 层 1:知识根基

**设计原则**:GEO Studio 不存原创素材,只**索引 + 引用**外部知识库。素材的所有权 / 版本 / 隐私级别归客户。

**为什么这样**:
- 客户(医院)有合规义务保管病历;知识不能离客户域,只能"借阅"
- 多客户接入时,知识库结构因行业而异(口腔 ≠ 医美 ≠ 律所),硬塞到一个 schema 不可行
- 素材更新频繁,跟着客户的 git 仓库 / 网盘走比 GEO Studio 自己存更新更快

**接入设计**:
- 知识库以**只读 git 仓库 / 文件夹**形式由客户提供
- GEO Studio 部署一个 sync agent:每天 pull 最新版本,扫描变更,增量索引
- 索引存在 GEO Studio 自己的 DB(`knowledge_sources` 表):路径 / 标题 / 首段摘要 / embedding,不存原文
- 内容生成时,RAG 召回 → **运行时**回 git 仓库读原文 → 注入 LLM context → 写完后引用源标记

**敏感数据处理**:
- 客户在知识库根目录放 `.geo-studio-allow` 文件白名单只暴露的目录(如 `患者/科普/`、`诊疗/项目库/`)
- L3 / L4 级数据(病例 / 投诉详情)不参与索引
- 自动遵守客户知识库的 `.kbignore` 规则

**现状 vs 目标**:

| | 现状(V1) | 目标(V1.5) |
|---|---|---|
| 素材入口 | 用户手工上传 Word/PDF | git sync + 增量索引 |
| 存储 | content_items 表存全文 | knowledge_sources 表存索引;原文按需读 |
| 引用追溯 | 无 | 每个变体带 source_path + line_range |

### 2.3 层 2:角度爆破

**设计原则**:**1 篇知识 × N 个受众维度** = N 篇有不同切入点的草稿。这是 SEO 时代"关键词矩阵"的进化版。

**为什么不只生成 1 篇**:
- AI 引擎在不同问题下偏好引用不同切入角度的内容(`种植牙怎么选医生` vs `糖尿病能种植牙吗` 答案构成不同)
- 同一受众能被 5-8 条不同角度的内容反复触达,SOV 累加
- 1 个事实素材爆破成 N 个变体,医生写 1 次 → 系统产出 5-10 篇

**实现**:
- 输入:主题 + 受众维度(三高 / 老人 / 青少年家长 / 孕妇 / 糖尿病 / ...)
- 系统:RAG 检索知识库 → 找 5-10 个相关片段
- 每个受众视角生成 1 篇草稿,带 GEO 9 法显式 prompt 指令(下一节)
- 草稿入 `content_items.status='ai_drafted'`,等医生 review

**关键约束**:
- AI 写完**必须**有医生审核确认(医学准确 + 合规 + 风格三重保险)
- 草稿明文标注引用源,医生改稿时可直接看到出处

**现状 vs 目标**:

| | 现状 | 目标 |
|---|---|---|
| AI 写作 | 没有,只能上传 | 有,主题 + 受众 + 平台 → N 篇草稿 |
| 角度维度 | n/a | 至少 5 个固定维度,V2 客户可自定义 |
| 医生审核流程 | 已有(content_items.status) | 加 ai_drafted 状态 + 改稿 UI |

### 2.4 层 3:平台变体(GEO 9 法)

**设计原则**:平台调性差异远大于行业差异。同一篇知乎风格的稿子在小红书反响为零,反之亦然。

**GEO 9 法**(经验加权重,基于 W6.0 探针 + 行业研究):
1. **加权威引用**(+41% 引用率):论文标题 / 学会指南 / 政策出处
2. **加统计数据**(+33%):数字 / 比例 / 临床研究结果
3. **加专家署名**(+28%):医生姓名 / 资质 / 案例
4. **加结构化标题**(+25%):一二三 / 小标题清晰
5. **加流畅度优化**(+22%):去除机器味
6. **加 quotation 直接引语**(+18%):"《XX 指南》指出..."
7. **加 explainer 解释性**(+15%):为什么这样做
8. **加 narrative 叙事**(+12%):案例故事化
9. **加 listicle 列表**(+8%):3 步 / 5 个要点

**平台差异化 prompt**:

| 平台 | 风格关键 | GEO 9 法重点 |
|---|---|---|
| 知乎 | 长文 + 引用 + 专业感 | 权威引用 + 数据 + 解释性 |
| 小红书 | 痛点开头 + 列表 + 个人化 | 叙事 + 列表 + 专家署名 |
| 抖音脚本 | 钩子 15 秒 + 视觉化 | 数据 + 直接引语(易转语音) |
| 公众号 | 故事化 + 图文 + 引导关注 | 叙事 + 解释性 + 权威引用 |
| 头条号 | 资讯感 + SEO 友好 | 权威引用 + 数据 + 结构化标题 |
| 百家号 | 类似头条号 | 同上 |

**现状 vs 目标**:

| | 现状 | 目标 |
|---|---|---|
| Prompt | 通用 9 法 prompt | 6 个平台各一套差异化 prompt |
| 9 法验证 | 无量化 | 加 A/B 测试基础设施(V2),量化每法贡献 |

### 2.5 层 4:三道门合规

**设计原则**:医疗 / 医美 / 律所等品类,合规是产品**底线**。三道门覆盖关键词 / 语义 / 人工三层防护。

**三道门**:
1. 关键词扫描(同步 < 50ms):A 级直接拒、B 级警告
2. LLM 语义审查(异步 < 3s):看上下文判断,关键词命中也可能因反例引用通过
3. 人工复核:B 级 + LLM 不确定的进队列

**接入知识库的合规**:
- 客户的 `合规/广告法/红线词库.md` 是**最权威的关键词库**(松鼠口腔已经维护,远比我们内置的 40+11 条全)
- 接入方式:同步到 `compliance_keywords` 表,客户更新 md 后自动 reindex
- 平台审核规则(`合规/广告法/平台审核规则/小红书.md` 等)作为 LLM prompt context

**新增第四道门(可选)**:
- 事实根基核对:草稿里的"5 年成功率 95%"这种数字,系统验证一下知识库里是否真有此数据
- 防 LLM 幻觉编数字
- V2 实现

**现状 vs 目标**:

| | 现状 | 目标 |
|---|---|---|
| 关键词库 | 40 A 级 + 11 B 级(代码内置) | 全部从客户知识库 sync,代码内不留 hardcoded |
| LLM 审查 | 通用 prompt | 注入客户的"平台审核规则" md 作为 context |
| 事实核对(第四道) | 无 | V2 实现(基于 RAG 反查) |

### 2.6 层 5:派单 + 真人发

**设计原则**:**真人发布永远不能自动化**(D3)。算法只决定"谁发什么",发布动作员工手工。

**派单算法**:
- 平台匹配(员工有的账号)
- 人设匹配(医生发种植内容、咨询发咨询话术、前台发就诊指引)
- 节奏控制(每人每天 ≤ 2 条)
- 新颖度(同员工不连发相似)

**用知识库的医生档案**:
- 9 个真实医生(周剑 / 张雷 / 潘娜 / 韩峄 / 伍思忆 / ...)直接 import 到 `staff_accounts`
- 每个医生档案里的"擅长项目"作为人设标签,自动匹配项目库内容

**员工端**:
- 移动 PWA 已上线
- 任务卡显示暗号 + 医生名钩子(已实现)
- 复制文案自动加 CTA(已实现)

**现状 vs 目标**:

| | 现状 | 目标 |
|---|---|---|
| 员工档案 | dev-seed 假数据(贾真真等) | 同步松鼠真实 9 医生 |
| 人设维度 | persona.tags 自由文本 | 从医生 md 解析"擅长项目"作为结构化标签 |

### 2.7 层 6:AI 引擎追踪

**设计原则**:必须模拟真人在 AI 引擎 Web 端提问,不能调 API(D4)。API 没 RAG 检索层,答案与真用户看到的不同。

**已实现(V1)**:豆包 Web,品牌词典 NER,SOV 计数

**V2 主菜**:
- 多引擎扩展:腾讯元宝、夸克 AI 超级框、DeepSeek、Kimi、文心一言
- 代理池 + 账号池(解开同 IP 限流)
- 追踪账号生命周期管理(创建 / 限流 / 封禁 / 替换)

**用知识库的品牌词典**:
- `团队/医生/*.md` → 9 个医生姓名 + 别名(贾医生 / 贾大夫)
- `诊疗/项目库/*.md` → 项目名 + 别名(种植牙 / 牙种植 / 人工牙根)
- `医院/竞品/*.md` → 竞品医院全名 + 别名
- 全部自动 sync 到 `brand_vocab` 表

**现状 vs 目标**:

| | 现状 | 目标 |
|---|---|---|
| 引擎覆盖 | 豆包 1 个 | V2 加 5 个,V3 加 ChatGPT/Perplexity 国际 |
| 词典维度 | 手动 dev-seed 20 条 | 从知识库 4 个目录 auto sync,V2 客户 admin UI 编辑 |
| 反爬 | 同 IP 限流(被动接受) | V2 代理池 + 账号池 |

### 2.8 层 7:转化归因

**设计原则**:不依赖前台问话,用多钩子被动回流(D6)。

**已实现**:暗号 + 医生名钩子,checkin 页,漏斗 + 单内容 ROI

**接入知识库后的升级**:
- 转化事件追溯到具体 publish_task(已有)
- publish_task 关联 variant 关联 content_item(已有)
- **content_item 关联 knowledge_source**(新做):新患者来店 → 哪条素材带来的 → 这素材源自知识库哪个 md
- 以**知识库素材粒度**统计 ROI

**反馈环(关键)**:
每周自动给医生发邮件:
> 上周 7 个新患者中,3 个来自基于「诊疗/项目库/种植/单颗种植.md」素材的内容。你的「糖尿病种植」方向素材带来 67% 的高质转化,建议下周扩写以下话题:..."

这是飞轮的核心动力 — 让医生写"被验证有效"的素材,不是凭感觉写。

**现状 vs 目标**:

| | 现状 | 目标 |
|---|---|---|
| 归因粒度 | 到 content_item | 到 knowledge_source |
| 反馈给医生 | 无 | 每周 AI 生成的"高 ROI 方向"建议 + 自动写作 prompt |

## 3. 数据模型扩展

### 3.1 新增表

```sql
-- 知识库索引
CREATE TABLE knowledge_sources (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id uuid NOT NULL REFERENCES tenants(id),
  source_path text NOT NULL,         -- e.g. "诊疗/项目库/种植/单颗种植.md"
  title text,                        -- 解析自 md H1
  excerpt text,                      -- 首段或 LLM 生成 200 字
  category text,                     -- 解析自 path 第一段 (诊疗/患者/营销/...)
  privacy_level text,                -- L1/L2/L3/L4 from CLAUDE.md frontmatter
  embedding vector(1536),            -- 豆包 / OpenAI embedding,V2 加
  source_hash text,                  -- 内容 SHA256,变更检测用
  ...timestamps()
);

-- 内容引用(content_item / variant 引用了哪些 knowledge_source)
CREATE TABLE content_citations (
  id uuid PRIMARY KEY,
  content_item_id uuid,              -- nullable
  variant_id uuid,                   -- nullable
  knowledge_source_id uuid NOT NULL,
  excerpt_used text,                 -- 实际引用的片段
  confidence float                   -- LLM 自评的引用紧密度
);

-- 反馈环:knowledge_source 维度的 ROI 聚合(物化视图)
CREATE MATERIALIZED VIEW source_attribution AS
SELECT
  ks.id, ks.source_path, ks.title,
  count(distinct ci.id) as content_count,
  count(distinct pt.id) as task_count,
  count(distinct ce.id) as conversion_count
FROM knowledge_sources ks
LEFT JOIN content_citations cc ON cc.knowledge_source_id = ks.id
LEFT JOIN content_items ci ON cc.content_item_id = ci.id
LEFT JOIN content_variants cv ON cv.content_item_id = ci.id
LEFT JOIN publish_tasks pt ON pt.variant_id = cv.id
LEFT JOIN hooks h ON h.publish_task_id = pt.id
LEFT JOIN conversion_events ce ON ce.hook_id = h.id
GROUP BY ks.id;
```

### 3.2 现有表的微调

- `content_items` 加列 `status='ai_drafted'`(医生待审 AI 草稿)
- `staff_accounts` 加列 `bio_md_path`(指向 `团队/医生/X.md` 的相对路径)
- `compliance_keywords` 加列 `source_path`(从知识库哪个 md 同步来,便于 reindex 时去重)

### 3.3 与现有 18 张表的关系

无破坏性改动。新表是 additive 的,RAG 写作不影响现有 W3-W7 任何流程。客户可以选择不接知识库,只用上传 Word(降级模式)。

## 5. 风险 + 护城河

### 5.1 真实风险(按概率 × 影响)

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| 豆包反爬升级,Playwright 失效 | 中 | 高 | 代理池 + 账号池 + 指纹隔离 + 多引擎分散 |
| 首客 6 个月引用率 < 10% | 中 | 高 | 每 2 周 checkpoint,低于预期先调内容策略不堆功能 |
| 医疗广告法罚单 | 低 | 致命 | 三道门 + audit_log + 客户签承诺书 |
| 员工号集体被封 | 中 | 中 | 不碰自动化 + 人设隔离 + 节奏控制 |
| 一人撑不住 V2 之后工作量 | 高 | 高 | V2 结束前招 1 个全栈 / AI 工程师 |
| 模仿者跟进(Athena / 知推等) | 高 | 中 | 转化归因闭环 + 知识库根基,壁垒时间换空间 |
| 豆包政策变化(字节封 GEO 工具) | 低 | 致命 | 多引擎策略 + 自托管不绑死任何家 |

### 5.2 护城河深度排序

1. **客户知识库** — 最深,客户写 6 个月的素材,竞品复制需要客户重新提供数据
2. **转化归因闭环** — 中等,3-6 个月技术 + 客户端推广可复制
3. **完整闭环工作流** — 浅,6 个月技术可追上(已有竞品在路上)
4. **GEO 改写 prompt** — 最浅,2-4 周可逆向

策略:把竞争重心放在加深 1 + 2(让客户更深绑定我们),不是堆 3 + 4 的功能数。
