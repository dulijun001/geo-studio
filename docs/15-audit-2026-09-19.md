# 15 — 全系统审计与重构蓝图（2026-09-19）

> 七个 agent 并行审计七个板块，全部结论要求给 `文件:行号` 或 SQL 证据，推测单独标注。
> 本文是审计结论 + 已修清单 + 未修的排期。决策摘要见 CLAUDE.md 的 D76。

## 一句话结论

**这个项目的问题不是功能不够，是「做了的东西没接通」。** 七个板块里最贵的几个 bug 有一个共同形态：
代码写对了、数据也产生了，但**中间少一根线**，于是整条链静默失效，没有任何报错。

三个最典型的：
- 告警全写好了 → `tenant_memberships` 空表 + 一个位置放错的 `continue` → **生产从未发出过一条**
- 稿子生成好了 → 客户端超时拿不到 id → **132 条孤儿稿永远不可派单**，还重复付费生成
- 任务派下去了 → 员工端一个时间窗过滤 → **12 个人全部看到「今日无任务」**，76% 被自动回收

## 未修 — 按优先级排期

### P0｜接第二家客户前必须做

**KB 根目录是全局单例。** `ai-draft-core.ts:125`、`kb-needle-lookup.ts:30`、`content/[id]/actions.ts:16`、
`derive-from-kb.ts:27` 全是模块级 `KB_ROOT`，无 tenant 入参；只有 `knowledge-sync.ts:257` 读了
`tenants.knowledge_base_path`。**租户 B 的稿子会引用租户 A 的诊疗事实。**
修法：`resolveKbRoot(tenantId)` 单点函数替换那 4 处。

**选题打分函数写死昆明。** `daily_ops_pick_topics` 把 14 个昆明行政区写进 SQL 的 `geo_tier CASE`。
新客所有题会被判 `geo_tier=2` 降级，选题带直接瘫。
修法：改读 `brands.service_areas`（0026 已建好字段，函数没用上）。

**RLS 在生产路径上是装饰品。** `current_user=postgres` 且 `rolbypassrls=t`；`supabase/server.ts:23-25`
在 admin cookie 存在时直接返回 service-role client。扫 `apps/web` 322 处租户表查询，**74 处邻近无
`tenant_id` 过滤**。隔离目前靠人工纪律，不靠数据库。
修法：admin 路径改走 `NOBYPASSRLS` 的应用角色。**注意**：审计只抽查了 2 处，未证实存在真实越权。

### P1｜影响判断质量

**questions 一表两用。** 建议**拆用途不拆表**：加 `usable_for text[]` + `track_priority` / `draft_priority`，
赋值规则并进已有的 `topic-priority.ts` 单点。理由：`questions` 有 44 处调用点，
`geo_snapshots.question_id` 与 `content_items.target_questions[]` 两条链都指着它，152 道题同时被追踪和起草
—— 不是两个互斥集合。冲突的本质只有「能不能用」「排多前」两个字段。

**第三道合规门（案例匹配）0/454 命中。** `case-match.ts:44` 要求 `matched>=2`，而库里
`violation_patterns` 存的是同一句话的同义词，数学上几乎不可能命中；且命中也只写字段不改状态，
与 docs/03 的设计不符。修法：patterns 改组结构（组内 OR、组间 AND），命中强制 pending，补 2025-26 罚单。

**误报率约 65%。** A 级 reject 词里「第一」17 次、「保证」14 次、「金牌」12 次，抽样 25 条「第一」
**25/25 全是合法用法**（第一恒磨牙 / ITI 第一组共识 / 第一步骤）。108 条被拒里大半是好稿，**0 条被人工救回**。
修法：词表加 `exempt_regex` 列；否定语境通用豁免；「冠军」「无痛」从 A 降 B 交给 LLM 判上下文。

**自动补货形同虚设。** `expand-subtopics.ts` 的提示词没有「只出找机构型」约束（D68 只改了打分没改生成端），
`topic-replenish.ts` 的水位计数不区分 priority。实测 llm_expand 产出 59 道只有 3 道可用。
修法：生成端加句式约束；水位只数 `questionPriority()>=11`；把 `_gen-seek-org-topics.ts` 从 `_dev/` 提为定时任务。

### P2｜债务

- **schema 包与库漂移**：`content_variants` 库里 6 列 schema 里一列没有；8 张生产表完全不在 schema 目录。
  比没有 schema 更危险，因为它看起来权威。
- 14 张初代表 `tenant_id` 无 FK（`_shared.ts:22` 的 `tenantFk()` 没有 `.references()`）。实测 0 孤儿行，补 FK 不会失败。
- `content_items.target_questions` 无 GIN 索引，picker RPC 每题全扫。
- `derive-from-kb.ts:608` 的 `if (term === '松鼠口腔')` —— D2 明令禁止的写法。
- 磁盘 94% 满（剩 53G）；备份无异地副本（154M，rsync 是分钟级的事）；日志在 `/tmp`（macOS 会清）。

## 明确不做

| 不做 | 理由 |
|---|---|
| 自助注册 / onboarding | 决定成败的 W0（KB / 词表 / 合规库）没法自助，KB 还在运维者本机。开了只会产出跑不出结果的空租户，还把医疗合规责任摊给不懂的人 |
| 计费系统 | 2 家客户用表格 + 转账。接支付是周级工作量 + 主体资质流程，5 家客户前是纯负债 |
| 自定义域名 / SSL | 同上 |
| 装 Sentry / Axiom | DSN 空放了 4 个月，说明不会去看。一个人只需要一条每天必到的心跳 |
| 夸克 / Kimi | 夸克撞阿里滑块（≈重做一个 CloakBrowser 级方案）；Kimi 在本地口腔检索的份额没有任何测量 |
| 全量内容过 LLM 语义门 | 3 倍调用量，而方舟欠费期间吃的是个人订阅额度。已用确定性检查堵住最高风险那一类 |

## 定价与交付形态（审计层面的判断）

**从系统现状看只能卖代运营，不能卖 SaaS 订阅**，五条系统层面的理由：
KB 入口依赖运维者本机手工建目录；合规人审是产线必需工序而非可选项；发布端是实名人肉账号（D3/D9）；
追踪是单一共享受限账号，容量随客户数线性吃紧（按席位定价单位经济学是反的）；没有一行计费代码。

**对外能讲**：提及率、名次（带板块）、引用源归属、合规拦截数 —— 都是自家系统实测。
**不能讲**：GEO 带来多少客户（`conversion_events` 0 行）、多引擎结论（此前仅豆包验证过）、排名承诺。

⚠️ **CLAUDE.md 第二节把「转化归因闭环」列为四条护城河之一，而 `conversion_events` / `hooks` /
`customer_identities` 全是 0 行。** 那一栏现在应该标「未建成」，不是「护城河」。docs/14 的「待补」段是诚实的，
CLAUDE.md 第二节不是。

## 审计方法与局限

七个 agent 并行，各自只读、禁止编造、结论须附 `文件:行号` 或 SQL。各 agent 自报的不确定项已保留在
原始输出中，其中影响结论的几条：

- undici `headersTimeout` 默认 300s 是推测，未在本机复现
- 74 处无 tenant 过滤只抽查了 2 处，**不能据此断言存在真实越权**
- 名次解出率低（8/100）有两个候选成因（`mapOffset` 差一位 / 多数题型本就不产生机构榜），未拆开
- 定价与市场部分全部为推测，无数据依据
- ECS 线上 worker 版本无法查看，`dist/` 是 5-25 旧产物
